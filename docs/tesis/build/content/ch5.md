> Capítulo 5. Implementación

Este capítulo documenta la construcción efectiva de CSLM: el entorno tecnológico y las dependencias utilizadas, la estructura de los proyectos de backend y frontend, la implementación de la persistencia y las migraciones, la seguridad, el proceso programado de notificaciones, la contenerización mediante Docker Compose y los datos de prueba cargados para la demostración y validación de la plataforma.

## 5.1 Entorno tecnológico

El backend se construyó con **Java 21** (la versión de soporte a largo plazo vigente al momento del desarrollo) y **Spring Boot 3**, gestionado mediante **Gradle** con *wrapper* incluido en el repositorio (`gradlew`), lo que garantiza que cualquier persona que clone el proyecto compile con exactamente la misma versión de Gradle sin necesidad de instalarla de forma independiente. Las dependencias principales, declaradas en `build.gradle`, son: `spring-boot-starter-web` (API REST), `spring-boot-starter-data-jpa` (persistencia sobre Hibernate), `spring-boot-starter-validation` (Bean Validation), `spring-boot-starter-security` (autenticación y autorización), `spring-boot-starter-mail` (envío de correo mediante Spring Mail), `flyway-core` y `flyway-mysql` (migraciones de base de datos), `springdoc-openapi-starter-webmvc-ui` (documentación OpenAPI/Swagger) y `jjwt-api` (emisión y verificación de JSON Web Tokens). Para pruebas se utilizan `spring-boot-starter-test` (JUnit 5, Mockito, AssertJ) y `spring-security-test`.

El frontend se construyó con **React 18**, **TypeScript**, **Vite** como herramienta de compilación y servidor de desarrollo, **Material UI (MUI)** como librería de componentes visuales, **React Router** para el enrutamiento entre pantallas y **Axios** como cliente HTTP, complementado con **React Flow** para la visualización del grafo de dependencias (sección 4.8).

La base de datos es **MySQL 8.0**, y el servidor de correo de desarrollo es **MailHog v1.0.1**. Todo el sistema se orquesta mediante **Docker Compose**, con imágenes construidas a partir de **Dockerfiles multi-etapa** tanto para el backend (`eclipse-temurin:21-jdk-alpine` para compilar, `eclipse-temurin:21-jre-alpine` para ejecutar, reduciendo el tamaño final de la imagen al no incluir el JDK completo ni las herramientas de compilación) como para el frontend (`node:22-alpine` para compilar los activos estáticos con Vite, `nginx:1.27-alpine` para servirlos).

## 5.2 Estructura del proyecto backend

El código fuente del backend se organiza bajo el paquete raíz `com.cslm`, con la siguiente distribución, ya introducida en la sección 4.3: `domain` (diecisiete clases de entidad JPA más tres enumeraciones de apoyo: `SemaphoreStatus`, `AssetCategory`, `LocationType` no como enumeración sino como catálogo — la única enumeración real de dominio es `SemaphoreStatus`, ya que los tipos de activo y de ubicación se modelan como catálogos en base de datos y no como enumeraciones de Java, precisamente para que sean administrables sin recompilar el backend), `repository` (interfaces `JpaRepository` con métodos de consulta derivados y, cuando fue necesario, `@Query` explícitas para las búsquedas multi-campo del requerimiento RF-13), `service` (veinte clases de servicio, una por área funcional), `controller` (catorce controladores REST), `dto` (catorce archivos, cada uno agrupando los DTO de un mismo agregado como clases anidadas), `security` (`JwtUtil`, `JwtAuthFilter`, `JwtProperties`, `CustomUserDetailsService`, `CurrentUser`), `audit` (`AuditService`), `scheduler` (`ExpirationNotificationJob`), `config` (`SecurityConfig`, `OpenApiConfig`) y `exception` (`GlobalExceptionHandler`, `ResourceNotFoundException`, `BadRequestException`).

Todas las clases de servicio utilizan inyección de dependencias por constructor, generada automáticamente mediante la anotación `@RequiredArgsConstructor` de Lombok sobre campos `final`, en lugar de inyección por campo (`@Autowired` directo sobre el atributo), lo que hace explícitas las dependencias de cada servicio en su firma de constructor y facilita la construcción de instancias de prueba sin necesidad de un contenedor de Spring en las pruebas unitarias (sección 6.2).

La configuración de la aplicación (`application.yml`) centraliza en un único archivo, mediante *placeholders* de Spring (`${VARIABLE:valor_por_defecto}`), la totalidad de los parámetros configurables del sistema: conexión a base de datos, configuración de Flyway, configuración de correo, la clave y el tiempo de expiración del token JWT, los orígenes permitidos para CORS y la expresión cron y la bandera de habilitación del proceso de notificaciones. Cada uno de estos *placeholders* tiene un valor por defecto seguro para desarrollo local (por ejemplo, apuntando a `localhost`), pero ninguno de esos valores por defecto es apto para producción sin ser sobrescrito explícitamente por una variable de entorno, y ninguno constituye una credencial real embebida en el repositorio.

## 5.3 Estructura del proyecto frontend

El frontend se organiza bajo `src/` en seis directorios: `api` (funciones tipadas de acceso a cada recurso de la API, construidas sobre una instancia común de Axios con interceptores de solicitud y de respuesta), `components` (componentes reutilizables entre pantallas: diálogos de formulario, el panel de despliegues, la vista de grafo, el indicador de semáforo), `contexts` (`AuthContext`, que expone el usuario autenticado, sus roles y las funciones de inicio y cierre de sesión a toda la aplicación mediante el patrón de contexto de React), `layout` (la estructura visual común: barra de navegación lateral, cabecera, área de contenido), `pages` (las doce pantallas descritas en la tabla 8) y `types` (definiciones TypeScript de los contratos de datos compartidos con el backend, mantenidas manualmente en correspondencia con los DTO de la sección 4.5). El enrutamiento, definido en `App.tsx` mediante React Router, protege las rutas que requieren autenticación redirigiendo al login cuando no existe un token válido en el contexto, y oculta —sin depender únicamente de dicha ocultación como control de seguridad, dado que la autorización real se aplica siempre en el backend— las acciones de escritura que el rol del usuario autenticado no tiene permitidas, mejorando la experiencia de uso sin sustituir el control de acceso del servidor.

## 5.4 Persistencia y migraciones

Toda la evolución del esquema de base de datos se gestiona mediante **Flyway**, con `ddl-auto: validate` configurado explícitamente en Hibernate —es decir, Hibernate verifica en el arranque que el esquema generado a partir de las entidades JPA coincide con el esquema real de la base de datos, pero nunca lo modifica automáticamente—, de modo que la única forma de cambiar la estructura de la base de datos es añadir un nuevo script de migración versionado. Esta decisión, deliberada, evita uno de los antipatrones más comunes en aplicaciones Spring Data JPA de nivel de madurez baja: dejar que Hibernate genere o altere el esquema de forma automática en cada arranque (`ddl-auto: update`), lo que dificulta el control de versiones del esquema y resulta inaceptable en un entorno productivo con datos reales.

El script `V1__init_schema.sql` (289 líneas) crea las diecisiete tablas descritas en la tabla 5, sus veintiséis restricciones de clave foránea, sus siete restricciones de unicidad y sus dieciocho índices adicionales, todo dentro del motor de almacenamiento InnoDB (que soporta transacciones y claves foráneas, a diferencia de MyISAM). El script `V2__seed_data.sql` (284 líneas) inserta el conjunto de datos de ejemplo utilizado tanto para la demostración descrita en el apéndice E como para las pruebas de integración del capítulo 6: tres usuarios (uno por rol), cuatro equipos, cinco ambientes, diez tipos de activo, once tipos de ubicación, ocho ubicaciones de despliegue concretas, cuatro aplicaciones, once certificados y cinco secretos, con fechas de vencimiento elegidas deliberadamente para cubrir los cinco estados del semáforo (por ejemplo, el certificado `api-prod` vence en 2027, muy dentro del rango verde; `corporate-prod` vence a solo cinco días de la fecha de referencia utilizada durante el desarrollo, cayendo en rojo; y el propio conjunto de datos deja evidencia, mediante el comentario `-- Reference date used to pick demo dates: 2026-09-05`, de la fecha respecto de la cual se calcularon esas distancias), así como las siete reglas de notificación y los tres umbrales del semáforo descritos en las secciones 4.7 y 4.9.

## 5.5 Seguridad implementada

La configuración de Spring Security (`SecurityConfig`) deshabilita la protección CSRF basada en cookies —apropiada para una aplicación que sirve HTML renderizado por el propio servidor, pero innecesaria e incluso contraproducente para una API sin estado consumida por un cliente que se autentica mediante un token portado explícitamente en cada petición—, configura la política de sesión como *stateless* (`SessionCreationPolicy.STATELESS`, de modo que Spring Security nunca crea ni depende de una `HttpSession`), instala el filtro `JwtAuthFilter` antes del filtro estándar de autenticación por usuario y contraseña, y declara la lista de orígenes permitidos para CORS a partir de la variable de entorno `CORS_ALLOWED_ORIGINS`, con los valores `http://localhost:5173` (servidor de desarrollo de Vite) y `http://localhost:8081` (frontend servido por Nginx en Docker Compose) habilitados por defecto.

El componente `JwtUtil` encapsula la generación y la verificación de tokens utilizando la librería `jjwt`, firmando cada token con una clave simétrica derivada de la variable de entorno `JWT_SECRET` y codificando en sus *claims* el nombre de usuario y la lista de roles, de modo que el filtro de autenticación no necesite consultar la base de datos en cada petición para conocer los roles del usuario —una optimización relevante en un sistema donde la mayoría de las peticiones son de lectura y donde minimizar la latencia de autorización es deseable—. El tiempo de expiración por defecto de ocho horas (`JWT_EXPIRATION_MINUTES=480`) equilibra la comodidad de no requerir un nuevo inicio de sesión durante una jornada laboral completa con la exposición limitada de un token potencialmente filtrado.

## 5.6 Proceso programado de notificaciones

El componente `ExpirationNotificationJob`, anotado con `@Scheduled(cron = "${cslm.notifications.cron}")`, se ejecuta —salvo que la bandera `NOTIFICATIONS_ENABLED` esté desactivada, en cuyo caso el propio componente omite su ejecución sin necesidad de eliminarlo del contexto de Spring— una vez al día a las 07:00 hora del servidor por defecto, expresión configurable mediante la variable de entorno `NOTIFICATIONS_CRON` sin requerir una recompilación. Su implementación, descrita en detalle en la sección 4.9, delega el cálculo de días restantes en `SemaphoreService`, la decisión de si corresponde notificar en `NotificationRuleService`, la construcción y el envío del correo en `NotificationService` (que utiliza `JavaMailSender` de Spring Mail sobre la configuración SMTP centralizada en `application.yml`) y el registro del resultado en `NotificationHistoryService`. El mismo `NotificationService` es invocado también, de forma síncrona y bajo demanda, por el endpoint `POST /api/notifications/test`, lo que permite a un usuario con rol ADMIN u OPERATOR verificar, desde la pantalla de detalle de un certificado o un secreto, que la configuración SMTP y la plantilla de correo funcionan correctamente sin esperar a la siguiente ejecución programada —mecanismo utilizado explícitamente durante la validación del flujo de aceptación descrita en el capítulo 6 y en el apéndice E—.

## 5.7 Contenerización y despliegue

El archivo `docker-compose.yml` define cuatro servicios: `mysql` (imagen oficial `mysql:8.0`, con un volumen nombrado `cslm-mysql-data` para persistir los datos entre reinicios del contenedor y una verificación de salud mediante `mysqladmin ping` antes de permitir que el backend inicie); `mailhog` (imagen `mailhog/mailhog:v1.0.1`, exponiendo el puerto 1025 para SMTP y el 8025 para su interfaz web de inspección de correo); `backend` (construido desde `backend/Dockerfile`, dependiente de que `mysql` reporte salud y de que `mailhog` haya iniciado, expuesto en el puerto 8080); y `frontend` (construido desde `frontend/Dockerfile`, dependiente de `backend`, expuesto en el puerto 8081 y mapeado internamente al puerto 80 de Nginx). La totalidad de la configuración sensible o dependiente del entorno —credenciales de base de datos, credenciales SMTP, la clave de firma JWT, los orígenes CORS permitidos y la expresión cron de notificaciones— se parametriza mediante variables de entorno con valores por defecto solo aptos para desarrollo local, documentadas de forma exhaustiva en un archivo `.env.example` que el usuario debe copiar a `.env` antes de ejecutar `docker compose up --build`, de modo que ninguna credencial real quede versionada en el repositorio (requisito no funcional descrito en la tabla 4).

El Dockerfile del backend sigue el patrón de **compilación multi-etapa**: una primera etapa, basada en `eclipse-temurin:21-jdk-alpine`, descarga las dependencias de Gradle en una capa de imagen separada de la copia del código fuente —de modo que un cambio en el código, sin cambios en `build.gradle`, no invalide la caché de dependencias ya descargadas— y compila el artefacto ejecutable (`bootJar`, omitiendo las pruebas para acelerar la construcción de la imagen, dado que las pruebas se ejecutan de forma independiente en el flujo de verificación descrito en el capítulo 6); una segunda etapa, basada en la imagen mucho más liviana `eclipse-temurin:21-jre-alpine` (que no incluye el compilador ni las herramientas de desarrollo del JDK completo), copia únicamente el artefacto compilado y lo ejecuta bajo un usuario no privilegiado creado explícitamente (`cslm`), en lugar de ejecutarlo como `root`, siguiendo el principio de menor privilegio también a nivel de contenedor. El Dockerfile del frontend sigue el mismo patrón: una etapa `node:22-alpine` compila los activos estáticos de producción con Vite, y una segunda etapa `nginx:1.27-alpine` los sirve, sin que la imagen final contenga Node.js, el código fuente TypeScript ni las dependencias de desarrollo.

## 5.8 Datos de prueba

Como se describió en la sección 5.4, el script `V2__seed_data.sql` deja la plataforma, inmediatamente después de su primer arranque, en un estado representativo de un entorno real de demostración: cuatro aplicaciones de distinta criticidad (Corporate Banking y Payments como críticas; Mobile Banking como alta; Treasury como media), cinco ambientes ordenados desde Desarrollo hasta Producción, y once certificados cuyas fechas de expiración fueron elegidas deliberadamente para que, en cualquier momento cercano a la fecha de referencia del conjunto de datos, el tablero de control muestre al menos un activo en cada uno de los cinco estados del semáforo, permitiendo verificar visualmente, sin necesidad de crear datos adicionales, que el cálculo descrito en la sección 4.7 se comporta como se espera en los cinco casos posibles. Este mismo conjunto de datos es la base sobre la que se ejecuta tanto la demostración manual del flujo de aceptación (apéndice E) como la prueba de integración automatizada descrita en la sección 6.3.
